Das token­sparende Stub-Modul

Programmatic Tool Calling (PTC) in Hermes — tools/code_execution_tool.py

Die Grundidee in einem Satz: Statt jedes Tool einzeln über das Modell laufen zu lassen (jedes Zwischenergebnis kostet Kontext), schreibt das Modell ein Python-Skript, das die Tools in einem Nebenprozess aufruft — und nur das fertige, kondensierte Ergebnis kommt zurück.

1 Das Problem: jedes Tool-Ergebnis klebt im Kontext

Ein normaler Agent, der 50 Webseiten einlesen und die relevante Zeile finden soll, macht 50 Runden. Jede Runde schiebt das volle Rohergebnis in den Kontext — und der Kontext wird bei jedem weiteren Model-Call komplett neu mitgeschickt.

Normaler Tool-Loop teuer

1web_extract(url 1) → 12 KB Rohtext+3k
2web_extract(url 2) → 9 KB Rohtext+2.4k
3web_extract(url 3) → 15 KB Rohtext+3.8k
…… 47 weitere Runden …+…
50web_extract(url 50)+2.9k
≈ 150 000 Tokens im Kontext
50 Model-Runden · alle Rohtexte bleiben liegen

Mit execute_code billig

1Modell schreibt 1 Skript~600
↻Skript loopt 50× im Nebenprozess0
🔒50 Rohtexte bleiben im Kind0
✓Skript print()et 8 Treffer-Zeilen~400
2Modell liest nur das Ergebnis—
≈ 1 000
2 Model-Runden · nur Skript + Endergebnis kosten Kontext

* Zahlen illustrativ. Der Punkt ist die Größenordnung: Kontextkosten skalieren nicht mehr mit der Anzahl der Tool-Calls, sondern nur noch mit der Größe des finalen Outputs.

2 Das „Stub-Modul": eine Attrappe der echten Tools

Wenn eine Session startet, generiert Hermes zur Laufzeit eine Datei hermes_tools.py. Für jedes der 7 erlaubten Sandbox-Tools (web_search, web_extract, read_file, write_file, search_files, patch, terminal) steht darin eine winzige Funktion — ein Stub. Der Stub tut die Arbeit nicht selbst; er reicht den Aufruf nur an den Elternprozess durch.

So sieht ein generierter Stub aus (aus generate_hermes_tools_module, Zeile 346):

# hermes_tools.py — zur Laufzeit erzeugt, liegt neben dem Skript
def web_extract(urls: list, char_limit: int = None):
    """Extract content from URLs. Returns dict with results list…"""
    return _call('web_extract', {"urls": urls, "char_limit": char_limit})

Der ganze Körper ist ein einziger _call(...). Das Modell sieht in seiner Anleitung genau diese Signaturen und ruft sie im Skript auf, als wären es normale Python-Funktionen — z. B. from hermes_tools import web_extract.

Und das ist _call — die Brücke, die aus einem Funktionsaufruf eine Nachricht an den Elternprozess macht (Zeile 460):

def _call(tool_name, args):
    request = json.dumps({
        "tool": tool_name,
        "args": args,
        "token": os.environ["HERMES_RPC_TOKEN"],   # Auth
    }) + "\n"
    with _call_lock:                 # ein Socket, seriell
        conn = _connect()             # AF_UNIX Socket zum Parent
        conn.sendall(request.encode())
        # … liest die Antwort bis zum Newline …
    return json.loads(raw)
Das Skript hat keinen direkten Zugriff auf Netzwerk-Keys, Suchmaschinen oder das Dateisystem-Tool. Es kann nur über das Socket „bitte web_extract" sagen. Der Elternprozess entscheidet, ob und wie das ausgeführt wird — dieselbe Kontrolle wie bei einem normalen Tool-Call.

3 Zwei Prozesse, ein Socket dazwischen

Der Trick lebt von der Trennung in zwei Betriebssystem-Prozesse, die über ein privates Unix-Socket reden:

🖥️ Elternprozess (Agent)
hat Modell, Credentials, die echten Tools
RPC-Server-Thread
lauscht am Socket, prüft Token handle_function_call()
derselbe Dispatcher wie bei normalen Tool-Calls 🔑 echte Tools: web, Dateien, Terminal
/tmp/hermes_rpc_<uuid>.sock
⟶
JSON-Request
+ Token
⟵
JSON-Ergebnis
chmod 0600 · Token-Auth
📦 Kindprozess (Sandbox)
frischer Python, Environment von Keys gesäubert
script.py
das vom Modell geschriebene Skript hermes_tools.py
die Stub-Attrappen → rufen _call() 🗑️ 50 Rohergebnisse leben & sterben hier

Der komplette Ablauf eines execute_code-Turns:

  1. Modell schreibt ein Skript und übergibt es dem execute_code-Tool.
    Das ganze Skript wird vorab genehmigt (Security-Guard), weil es beliebiges Python ausführen könnte.
  2. Parent erzeugt hermes_tools.py (Stubs) + ein Zufalls-Token, öffnet ein privates Unix-Socket und startet einen Lausch-Thread.
  3. Parent startet einen Kindprozess für das Skript — mit von API-Keys/Tokens gesäubertem Environment. Das Kind kennt nur Socket-Pfad und Token.
  4. Das Skript ruft web_extract(...) auf → der Stub schickt JSON durchs Socket → der Parent führt das echte Tool aus → schickt das Ergebnis zurück. Das wiederholt sich, so oft das Skript will (bis 50×).
  5. Alle Zwischenergebnisse bleiben als Variablen im Kind. Das Skript filtert/aggregiert und gibt per print() nur das Wesentliche aus.
  6. Der Parent fängt nur den stdout des Skripts ab (gedeckelt auf 50 KB) und gibt ihn als Tool-Ergebnis ans Modell zurück.
Das ist der „Zero-Context"-Kern: Die 50 web_extract-Ergebnisse laufen zwar wirklich durch den Agenten — aber sie fließen durch das Socket in den Kindprozess und verpuffen dort. Ins Kontextfenster des Modells kommt nur, was das Skript am Ende print()et.

4 Ein konkretes Skript

So könnte das Modell „durchsuche diese 50 Release-Notes nach Breaking Changes" in einem Turn lösen:

from hermes_tools import web_extract

urls = [ "https://…/v1", "https://…/v2", # … 50 URLs ]

hits = []
for url in urls:
    res = web_extract([url])                    # ← RPC in den Parent, Rohtext bleibt hier
    text = res["results"][0]["content"]
    for line in text.splitlines():
        if "breaking change" in line.lower():
            hits.append(f"{url}: {line.strip()}")

# NUR das hier kostet Kontext:
print(f"{len(hits)} Breaking Changes gefunden:")
print("\n".join(hits[:20]))

50 Seiten à ~10 KB (= ~150k Tokens Rohtext) werden gelesen, aber das Modell sieht am Ende nur die ~20 Treffer-Zeilen. Dazu kommen eingebaute Helfer im Stub-Modul (json_parse, shell_quote, retry) gegen typische Skript-Fallen.

5 Warum das für AIpaca besonders zählt

Der teuerste Constraint auf einem Handy ist das winzige Kontextfenster eines on-device-Modells. Ein 3B-Modell kann keine 50 Zwischenergebnisse halten — mit diesem Muster muss es das auch nicht. Es schreibt ein kleines Skript, und die Batch-Arbeit passiert außerhalb des Kontexts. Der Mechanismus ist reines OS-Handwerk (Subprozess + Socket), völlig modell-unabhängig.

Eine Anpassung fürs Handy: Androids Prozess-Isolation ist restriktiver als auf einem Server. Statt eines vollen Subprozesses würde man on-device eher einen eingebetteten Interpreter mit sauberem Namespace nehmen — aber das Grundprinzip „Modell schreibt Skript, Tools laufen außerhalb des Kontexts, nur das Ergebnis kommt zurück" bleibt identisch und ist genau das, was Multi-Step-Arbeit auf kleinen Modellen überhaupt erst ermöglicht.
